### Module 5 — Lambda Event Sources, Triggers, and Event-Driven Integrations

### 1\. Introduction to Lambda Event Sources

One of the most important capabilities of AWS Lambda is its ability to execute code automatically when something happens in another AWS service.

Instead of continuously running an application and checking whether something needs to be processed, Lambda can respond to events generated by other services.

For example:

* A user uploads an image to Amazon S3.

* A new message arrives in an SQS queue.

* A database record changes in DynamoDB.

* An event is published to EventBridge.

* An HTTP request reaches API Gateway.

* A scheduled event occurs.

Lambda can automatically execute a function in response to these events.

This is the foundation of event-driven architecture (EDA).

### 1.1 What is an event?

An event is a record describing something that happened in a system.

For example, when a user uploads a file to S3, AWS can generate an event containing information such as:

* Event type.

* Bucket name.

* Object key.

* Event timestamp.

* Object version information, where applicable.

A simplified S3 event might look like this:

```json
{
  "Records": [
    {
      "eventSource": "aws:s3",
      "eventName": "ObjectCreated:Put",
      "s3": {
        "bucket": {
          "name": "my-upload-bucket"
        },
        "object": {
          "key": "uploads/image.jpg",
          "size": 204800
        }
      }
    }
  ]
}
```

Lambda receives this event through its handler:

```python
def lambda_handler(event, context):
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = record["s3"]["object"]["key"]

        print(f"New object: s3://{bucket}/{key}")

    return {"statusCode": 200}
```

The event is the input to the function. The function processes it and optionally interacts with other AWS services.

### 1.2 Event source architecture

There are two important ways AWS services integrate with Lambda:

A. Push-based invocation

The event source directly invokes the Lambda function when an event occurs.

Examples:

* S3 notifications.

* SNS notifications.

* EventBridge events.

* API Gateway requests.

B. Poll-based invocation

Lambda manages an event source mapping that polls or reads from another service and invokes the function when records are available.

Examples:

* SQS.

* DynamoDB Streams.

* Kinesis Data Streams.

The distinction is important because it affects scaling, retries, batching, permissions, and failure handling.

### 1.3 Direct integrations versus event source mappings

Not every integration uses the same mechanism.

| Integration      | Mechanism                   |
| ---------------- | --------------------------- |
| S3               | Direct service notification |
| SNS              | Direct invocation           |
| EventBridge      | Direct invocation           |
| API Gateway      | Direct invocation           |
| SQS              | Event source mapping        |
| DynamoDB Streams | Event source mapping        |
| Kinesis          | Event source mapping        |

For direct integrations, the source service generally sends an invocation request to Lambda.

For polling integrations, Lambda reads records from the source and invokes your function with batches of records.

Important distinction: An event source mapping is an AWS resource that connects a supported event source to a Lambda function. It controls polling, batching, filtering, and other processing behavior.

### 2\. Direct Service Integrations and Event Notifications

Direct service integrations allow AWS services to invoke Lambda functions without requiring your application to continuously poll for events.

Consider an application that processes uploaded documents.

The architecture could be:

![Going Serverless - Get Started with AWS Lambda | Webiny](https://images.openai.com/static-rsc-4/9Yf11fZxzwaRJG4PsAmgreXODMkYhiTQ8fjQBEImASJo0yyVruRbs-eAhS4ZNACM3ikjxsb0UyeTh8smgtqk_iNWq_V4w2Olb-qVpBSK9B_xiJNp94STTRCPrDXSJON7y6bX3_IUX2aTcCqTHVcPMMERAwsnZnf8ldl3LIbAzY9Jkfa7HPjBOVncelInixW7?purpose=fullsize)

* A user uploads a document.

* S3 generates an object-created event.

* S3 sends a notification to Lambda.

* Lambda executes.

* Lambda processes the document.

* The result is stored in another AWS service.

This approach eliminates the need for a continuously running worker.

### 2.1 Resource-based policies

For many direct integrations, the source service needs permission to invoke the Lambda function.

Lambda uses resource-based policies to grant permissions to external AWS services.

For example, you can allow a particular S3 bucket to invoke a Lambda function:

```bash
aws lambda add-permission \
  --function-name document-processor \
  --statement-id allow-s3-invoke \
  --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::my-upload-bucket \
  --source-account 123456789012
```

Here:

* `--function-name` identifies the Lambda function.

* `--action` specifies the permitted action.

* `--principal` identifies the service.

* `--source-arn` restricts which bucket can invoke the function.

* `--source-account` adds an account-level restriction.

This is different from the Lambda execution role.

Remember:

* Execution role: What the Lambda function is allowed to do.

* Resource-based policy: Who or what is allowed to invoke the Lambda function.

### 3\. Amazon S3 Event Notifications and Object Processing

Amazon S3 can generate event notifications when objects are created, deleted, restored, or otherwise changed through supported operations.

These events can trigger Lambda functions automatically.

### 3.1 Supported S3 event categories

Common event types include:

| Event              | Description            |
| ------------------ | ---------------------- |
| s3:ObjectCreated:* | Object creation        |
| s3:ObjectRemoved:* | Object deletion        |
| s3:ObjectRestore:* | Object restoration     |
| s3:ObjectTagging:* | Object tagging changes |
| s3:ObjectAcl:*     | Object ACL changes     |

You can configure notifications for specific event types.

### 3.2 Filtering S3 notifications

Suppose your application stores multiple types of files:

```text
uploads/
    images/
    documents/
    videos/
```

You may want a Lambda function to process only images.

S3 notifications support prefix and suffix filters.

Example:

* Prefix: `uploads/images/`

* Suffix: `.jpg`

This means the notification is generated only for matching object keys.

Filtering helps reduce unnecessary Lambda invocations.

### 3.3 Avoiding recursive invocation

A common architectural mistake occurs when a Lambda function writes its output into the same bucket that triggers it.

For example:

```text
S3 upload
    |
    v
Lambda
    |
    v
S3 output upload
    |
    v
Lambda
    |
    v
S3 output upload
    |
    v
...
```

This creates an invocation loop.

You can prevent it by:

* Using separate input and output buckets.

* Filtering notifications by prefixes.

* Filtering notifications by suffixes.

* Separating processing responsibilities.

### 3.4 Example: Image processing

Imagine an image-processing application.

```text
User uploads image
        |
        v
S3 Input Bucket
        |
        v
S3 Event Notification
        |
        v
Lambda Image Processor
        |
        v
Resize / Compress Image
        |
        v
S3 Processed Bucket
```

The Lambda function could use Pillow to resize images.

The execution role needs permission to read from the input bucket and write to the output bucket.

### 3.5 Important S3 considerations

S3 event notifications are delivered at least once, and events can arrive out of order.

Therefore:

* Do not assume exactly-once execution.

* Design processing to be idempotent.

* Do not assume events arrive in chronological order.

* Account for URL encoding in object keys.

* Consider object versioning when processing versioned objects.

These considerations become particularly important in production applications.

### 4\. DynamoDB Streams Integration

DynamoDB Streams capture changes made to items in a DynamoDB table.

Instead of querying the table repeatedly to discover changes, applications can consume the stream of database modifications.

### 4.1 How DynamoDB Streams work

When an item changes, DynamoDB Streams can generate a record describing the modification.

For example:

```text
DynamoDB Table
      |
      | Insert / Modify / Remove
      v
DynamoDB Stream
      |
      v
Lambda Event Source Mapping
      |
      v
Lambda Function
      |
      v
Process Change
```

A stream record can contain:

* Event name.

* Sequence number.

* Stream ARN.

* Approximate creation timestamp.

* Previous item image.

* Updated item image.

### 4.2 Stream view types

DynamoDB provides four stream view types:

| Stream view        | Information                     |
| ------------------ | ------------------------------- |
| KEYS_ONLY          | Primary key attributes only     |
| NEW_IMAGE          | Entire item after modification  |
| OLD_IMAGE          | Entire item before modification |
| NEW_AND_OLD_IMAGES | Both previous and updated items |

For example, if you need to compare a product's old and new prices, `NEW_AND_OLD_IMAGES` is useful.

### 4.3 Lambda integration

Lambda uses an event source mapping to read DynamoDB Stream records.

Example:

```python
def lambda_handler(event, context):
    for record in event["Records"]:
        event_name = record["eventName"]

        if event_name == "INSERT":
            new_item = record["dynamodb"].get("NewImage")
            print("New item:", new_item)

        elif event_name == "MODIFY":
            old_item = record["dynamodb"].get("OldImage")
            new_item = record["dynamodb"].get("NewImage")

            print("Old:", old_item)
            print("New:", new_item)

        elif event_name == "REMOVE":
            old_item = record["dynamodb"].get("OldImage")
            print("Removed:", old_item)
```

### 4.4 Shards and ordering

DynamoDB Streams organize records into shards.

Lambda processes records from each shard in sequence-number order.

This provides ordering within a shard, but you should not assume global ordering across all records or shards.

### 4.5 Important configuration

When creating the event source mapping, you can configure:

* Starting position: `LATEST` or `TRIM_HORIZON`.

* Batch size.

* Maximum batching window.

* Parallelization factor.

* Retry attempts.

* Maximum record age.

* Failure destinations.

* Bisect batch on function error.

* Partial batch failure reporting.

DynamoDB Streams retain stream records for 24 hours.

This is an important operational constraint: consumers must process records within the retention period.

Amazon Kinesis Data Streams is designed to collect and process real-time streaming data.

Typical use cases include:

* Application logs.

* IoT telemetry.

* Clickstream data.

* Financial transactions.

* Real-time analytics.

* Monitoring events.

Lambda can consume Kinesis records through an event source mapping.

![Best practices for consuming Amazon Kinesis Data Streams using AWS Lambda | AWS Big Data Blog](https://images.openai.com/static-rsc-4/tMpEAiBEHzIsTyoPMmrlL5jtQ5C4pzKA4rydz2oiw-LXTjELCz05HUCRkQDyDdy_yB7hFY-n_sGUGB_oJoaLU54vH14VXK6qykbZEk6DPjPSDE9Q4GBMos1B60nVrBn9h9BzhFuriaAQU3xNxF00WOaqI3ccOThmHndDaX1alw5Hyr6Qm2CXOSa8LSr9kBHy?purpose=fullsize)

### 5.1 Kinesis architecture

A simplified architecture:

```text
Data Producers
      |
      v
Kinesis Data Stream
      |
      v
Shards
      |
      v
Lambda Event Source Mapping
      |
      v
Lambda Function
      |
      v
Data Processing / Storage
```

Producers send records to Kinesis.

Kinesis stores these records in shards.

Lambda reads records from the stream and invokes the function with batches.

### 5.2 What is a shard?

A shard is a unit of capacity in Kinesis Data Streams.

Each shard provides a specific amount of read and write throughput.

Records are assigned to shards based on their partition keys.

For example:

```text
Partition key: customer-100
Partition key: customer-200
Partition key: customer-300
```

Records sharing the same partition key are directed to the same shard, preserving their relative ordering within that shard.

### 5.3 Lambda polling modes

Lambda supports different polling approaches for Kinesis:

* Standard polling.

* Enhanced fan-out.

With standard polling, Lambda shares the stream's read throughput with other consumers.

Enhanced fan-out provides dedicated throughput for registered consumers through a push-based HTTP/2 streaming connection from Kinesis.

This can improve throughput isolation and reduce consumer contention.

### 5.4 Important event source mapping settings

Kinesis integrations support:

* Batch size.

* Maximum batching window.

* Starting position.

* Parallelization factor.

* Bisect batch on error.

* Partial batch responses.

* Retry attempts.

* Maximum record age.

* On-failure destinations.

* Filtering criteria.

### 5.5 DynamoDB Streams versus Kinesis

Both services can integrate with Lambda using event source mappings, but their purposes differ.

| Feature         | DynamoDB Streams         | Kinesis Data Streams        |
| --------------- | ------------------------ | --------------------------- |
| Primary purpose | Database change capture  | General-purpose streaming   |
| Data source     | DynamoDB table changes   | Multiple producers          |
| Ordering        | Per shard                | Per shard and partition key |
| Retention       | 24 hours                 | Configurable                |
| Typical use     | Database synchronization | Real-time data processing   |

Use DynamoDB Streams when you need to react to database changes.

Use Kinesis when you need a general-purpose streaming platform.

### 6\. Amazon SQS Event Source Mappings

Amazon SQS is one of the most important Lambda integrations because it enables asynchronous processing and application decoupling.

Instead of invoking Lambda directly whenever an application generates work, the application publishes a message to an SQS queue.

Lambda retrieves messages from the queue and processes them.

![The Essential Guide to Amazon SQS | Baselime Blog](https://images.openai.com/static-rsc-4/4ryjXbO7OehqPi_J_8_jWRRPQiTjhRjs_AWUIx5N42tC6S3_s4KmWI3zQ7TjxMdLZI46pxqGN0kqXQYOPxWgrPlmvG_wLlRqWyo8pjYD33dwMEUcdX9LPWxa3D0AX7e_K2OMDeMahCib_ldBnf-H11wYsz-kYZFshYR5vYb3lg-P4LwhjAl_3K6CxxbcySv-?purpose=fullsize)

### 6.1 How SQS integrates with Lambda

The processing flow is:

```text
Application
     |
     v
SQS Queue
     |
     v
Lambda Polling
     |
     v
Batch of Messages
     |
     v
Lambda Function
     |
     v
Process Messages
     |
     v
Delete Successfully Processed Messages
```

An important detail: Lambda manages the polling infrastructure for SQS event source mappings. You don't need to implement your own polling loop.

Lambda receives messages in batches.

For example, suppose your queue contains 1,000 messages and your configured batch size is 100.

Lambda can process these messages in multiple invocations, with concurrency determined by queue traffic, available concurrency, and event source mapping configuration.

### 6.2 Standard queues versus FIFO queues

SQS provides two main queue types.

| Feature        | Standard            | FIFO                                                                       |
| -------------- | ------------------- | -------------------------------------------------------------------------- |
| Ordering       | Best effort         | Preserved within message groups                                            |
| Delivery       | At least once       | Exactly-once processing deduplication features, with important limitations |
| Throughput     | Very high           | Depends on FIFO configuration                                              |
| Message groups | No                  | Yes                                                                        |
| Deduplication  | Application-managed | Deduplication support                                                      |

FIFO queues are particularly useful when ordering is important.

For example, consider a banking application:

```text
Account: 1001

1. Deposit $100
2. Withdraw $50
3. Deposit $200
```

The application must process these operations in the correct order.

A FIFO queue with an appropriate message group ID can preserve the order of operations for that account.

Important: FIFO queue deduplication does not guarantee that your business operation executes exactly once. Your application should still implement idempotency.

### 6.3 Visibility timeout

When Lambda receives a message from SQS, that message becomes temporarily invisible to other consumers.

This is called the visibility timeout.

For example:

```text
SQS Queue
    |
    v
Lambda receives message
    |
    v
Message becomes invisible
    |
    v
Lambda processes message
    |
    v
Successful processing
    |
    v
Message deleted
```

If processing fails and the message is not deleted, it can become visible again after the visibility timeout.

The visibility timeout should be configured carefully.

AWS recommends setting the queue visibility timeout to at least six times the Lambda function timeout, plus the maximum batching window when one is configured.

This provides room for retries and throttling-related delays.

### 6.4 Batch processing

SQS event source mappings support batch processing.

Important configuration parameters include:

* Batch size.

* Maximum batching window.

* Maximum concurrency.

* Provisioned pollers, where supported.

* Scaling configuration.

For standard queues, the maximum batch size is 10,000 messages. For FIFO queues, it is 10 messages.

The actual batch size depends on the available messages and configuration.

### 6.5 Partial batch failure handling

One important problem with batch processing is that a single failed message can cause successfully processed messages to be retried unnecessarily.

Consider this batch:

```text
Message 1 → Success
Message 2 → Success
Message 3 → Failure
Message 4 → Success
Message 5 → Success
```

Without partial batch response support, the entire batch may be retried.

This creates unnecessary processing and can cause duplicate operations.

Lambda supports partial batch responses using the `ReportBatchItemFailures` feature.

Example:

```python
def lambda_handler(event, context):
    batch_item_failures = []

    for record in event["Records"]:
        try:
            process_message(record)

        except Exception:
            batch_item_failures.append({
                "itemIdentifier": record["messageId"]
            })

    return {
        "batchItemFailures": batch_item_failures
    }
```

You must enable the `ReportBatchItemFailures` response type in the event source mapping.

Now Lambda can identify which messages failed rather than treating the entire batch as unsuccessful.

### 6.6 Dead-letter queues

A dead-letter queue (DLQ) stores messages that cannot be successfully processed after repeated attempts.

For example:

```text
Main SQS Queue
      |
      v
Lambda
      |
      v
Processing Failure
      |
      v
Retry
      |
      v
Repeated Failure
      |
      v
Dead-Letter Queue
```

This prevents problematic messages from remaining indefinitely in the main processing flow.

There is an important distinction:

* An SQS redrive policy moves messages to another queue after their receive count exceeds the configured maximum.

* Lambda asynchronous invocation destinations and DLQs are different mechanisms and are not used for ordinary SQS event source mapping failures.

For SQS-triggered Lambda functions, use the source queue's redrive policy and DLQ configuration.

### 7\. Amazon SNS Integration

Amazon SNS (Simple Notification Service) provides publish/subscribe messaging.

Unlike SQS, which primarily provides message queuing, SNS distributes messages to multiple subscribers.

Lambda can subscribe directly to SNS topics.

![Amazon SNS vs. Amazon SQS: A simple comparison | Shikisoft Blog](https://images.openai.com/static-rsc-4/xp-eGacF8UCGhvWKmjsU3Otrh0XR1TjWpjAKtZcqjtSSpiUqBdLqDd27_H5KmQd54hJ3volsTvglvIJ29Wyn0IDo8PT2wuY4nz-dFE5TdfIp9eWtXu1Ml-2AqGy6zqaA3T7whPbq-kSTSnnbloeyuODDb12oqOa2cNmwY__I9j38d_VaSlR0C6KAy4kSi4tm?purpose=fullsize)

### 7.1 SNS architecture

SNS uses three major concepts:

* Publisher: The application or service publishing a message.

* Topic: The logical communication channel.

* Subscriber: The service or endpoint receiving the message.

For example:

```text
Application
     |
     v
SNS Topic
     |
     +-----------> Lambda Function A
     |
     +-----------> Lambda Function B
     |
     +-----------> SQS Queue
     |
     +-----------> Email Subscription
```

This architecture is called fanout.

One message can be distributed to multiple independent consumers.

### 7.2 SNS-to-Lambda integration

When an SNS topic invokes Lambda:

* The publisher sends a message to SNS.

* SNS receives the message.

* SNS identifies its subscribers.

* SNS invokes subscribed Lambda functions.

* Lambda processes the notification.

The Lambda function receives an SNS event.

Example:

```python
def lambda_handler(event, context):
    for record in event["Records"]:
        sns_message = record["Sns"]["Message"]

        print("Received message:", sns_message)

        process_notification(sns_message)

    return {"statusCode": 200}
```

Notice that the message is inside:

```python
record["Sns"]["Message"]
```

This is different from the event structure received from SQS.

### 7.3 SNS subscription filtering

Suppose an e-commerce application publishes events such as:

```json
{
  "eventType": "ORDER_CREATED",
  "priority": "HIGH",
  "orderId": "ORD-1001"
}
```

You might have multiple subscribers:

* Order processing.

* Customer notifications.

* Analytics.

* Fraud detection.

Not every subscriber needs every message.

SNS supports subscription filter policies.

For example, a subscriber can receive only events where:

```json
{
  "priority": ["HIGH"]
}
```

SNS evaluates the filter policy against message attributes by default.

You can also configure filtering against the message body.

Filtering reduces unnecessary message delivery and processing.

### 7.4 SNS delivery retries and failures

SNS retries delivery when a supported endpoint cannot successfully receive a message.

For Lambda subscriptions, SNS uses its delivery retry policy.

You can configure a subscription DLQ to capture messages that cannot be delivered successfully after retries.

Remember that SNS delivery retries and Lambda asynchronous invocation retries are separate from SQS message visibility and redrive behavior.

### 7.5 SNS versus SQS

| Feature            | SNS                            | SQS                    |
| ------------------ | ------------------------------ | ---------------------- |
| Messaging pattern  | Publish/subscribe              | Queue-based            |
| Main purpose       | Message distribution           | Message buffering      |
| Multiple consumers | Fanout                         | Competing consumers    |
| Message retention  | Short-lived delivery mechanism | Configurable retention |
| Message polling    | No                             | Yes                    |
| Ordering           | No general ordering guarantee  | FIFO supports ordering |
| Typical use        | Notifications                  | Background processing  |

A particularly powerful architecture combines both services:

```text
                Application
                     |
                     v
                  SNS Topic
                     |
           +---------+---------+
           |         |         |
           v         v         v
         SQS A     SQS B     Lambda C
           |         |
           v         v
        Lambda A  Lambda B
```

This architecture provides independent queues for different consumers.

It also allows each consumer to process messages at its own speed.

### 8\. Amazon EventBridge Rules and Event Buses

Amazon EventBridge is a serverless event-routing service.

It receives events from AWS services, custom applications, and supported SaaS integrations, then routes matching events to configured targets.

Lambda is one of its most common targets.

![Modernizing Legacy Applications with Event-Driven Architecture: The Leave-and-Layer Pattern | Migration & Modernization](https://images.openai.com/static-rsc-4/ydl0QIfaGYAPqOs0Jb_i8g-hemF9fOb0rd6vfUEdiV89rRzCGCBJRrjSYUWcuuLzB6hAohIIynjh69999Cy-A0BiCEdXrPcBViA_H_5toiKpPRPHoG4PCmmXAcZWf4238dx_Z2Fxq9ryWivsXZpFtYAkwrXhRNgVqzp-yo5DLE3URJ_bKlSuI_gRlfpdK1uK?purpose=fullsize)

### 8.1 EventBridge architecture

The main components are:

* Event producers.

* Event buses.

* Event rules.

* Event patterns.

* Targets.

A typical architecture:

```text
AWS Services / Applications
            |
            v
       Event Bus
            |
            v
       Event Rules
            |
       +----+----+
       |         |
       v         v
    Lambda A  Lambda B
```

The event bus receives events.

Rules determine which events should be routed to which targets.

### 8.2 Event buses

EventBridge supports several event bus types:

| Event bus | Purpose                                      |
| --------- | -------------------------------------------- |
| Default   | Receives events from AWS services            |
| Custom    | Receives application-generated events        |
| Partner   | Receives events from supported SaaS partners |

For example, an application could publish an event:

```json
{
  "Source": "com.shop.orders",
  "DetailType": "OrderCreated",
  "Detail": {
    "orderId": "ORD-1001",
    "customerId": "CUS-2001",
    "amount": 250
  }
}
```

This event can be routed to different Lambda functions based on its content.

### 8.3 Event patterns

An EventBridge rule uses an event pattern to determine whether an incoming event matches certain conditions.

Example:

```json
{
  "source": ["com.shop.orders"],
  "detail-type": ["OrderCreated"],
  "detail": {
    "amount": [
      {
        "numeric": [">", 100]
      }
    ]
  }
}
```

This rule matches order-created events where the amount is greater than 100.

Matching events are sent to the configured target.

### 8.4 EventBridge targets

EventBridge supports many target types, including:

* Lambda functions.

* SQS queues.

* SNS topics.

* Step Functions state machines.

* ECS tasks.

* API destinations.

* Other event buses.

This makes EventBridge useful for connecting distributed applications without tightly coupling their components.

### 8.5 EventBridge versus SNS

Both SNS and EventBridge distribute events, but they have different strengths.

| Feature               | SNS                            | EventBridge                 |
| --------------------- | ------------------------------ | --------------------------- |
| Main purpose          | Pub/sub messaging              | Event routing               |
| Filtering             | Subscription filter policies   | Rich event patterns         |
| Event structure       | Message-oriented               | Structured event envelope   |
| AWS service events    | Through supported integrations | Native integration          |
| Custom event buses    | No                             | Yes                         |
| Scheduled execution   | Not its primary role           | Supported through Scheduler |
| Cross-account routing | Supported                      | Supported                   |

Use SNS when you need straightforward message distribution.

Use EventBridge when you need sophisticated event routing, event buses, and integration across multiple systems.

### 9\. API Gateway and Lambda Integration

API Gateway allows applications to expose HTTP APIs backed by Lambda functions.

This is one of the most common architectures for serverless backend development.

### 9.1 Request-response architecture

Consider a FastAPI-style backend implemented using Lambda.

The request flow:

```text
Client
  |
  v
API Gateway
  |
  v
Lambda Function
  |
  v
Business Logic
  |
  v
DynamoDB
  |
  v
HTTP Response
```

When a client sends an HTTP request:

* API Gateway receives the request.

* API Gateway routes it to the appropriate integration.

* Lambda executes.

* Lambda processes the request.

* Lambda returns a response.

* API Gateway sends the HTTP response to the client.

### 9.2 API Gateway integration types

API Gateway supports several integration options.

For Lambda applications, the most important is Lambda proxy integration.

With proxy integration, API Gateway forwards the request information to Lambda in an event object.

Example:

```json
{
  "version": "2.0",
  "routeKey": "POST /orders",
  "rawPath": "/orders",
  "headers": {
    "content-type": "application/json"
  },
  "body": "{\"product_id\":1001,\"quantity\":2}",
  "isBase64Encoded": false
}
```

The Lambda function processes this event and returns a structured response.

Example:

```python
import json

def lambda_handler(event, context):
    body = json.loads(event.get("body") or "{}")

    response_body = {
        "message": "Order created",
        "product_id": body.get("product_id")
    }

    return {
        "statusCode": 201,
        "headers": {
            "Content-Type": "application/json"
        },
        "body": json.dumps(response_body)
    }
```

The main API Gateway options are:

| Type          | Characteristics                       |
| ------------- | ------------------------------------- |
| HTTP API      | Lightweight, cost-effective HTTP APIs |
| REST API      | More advanced API management features |
| WebSocket API | Persistent two-way communication      |

For many new serverless HTTP backends, HTTP APIs are a good starting point.

REST APIs are useful when you need their additional API management capabilities.

### 9.4 Authentication and authorization

API Gateway can integrate with:

* IAM authorization.

* JWT authorizers.

* Lambda authorizers.

* Amazon Cognito.

The choice depends on your application security requirements.

For example, a SaaS application might use JWT authorization to validate access tokens before requests reach Lambda.

### 9.5 API Gateway versus Lambda Function URLs

Lambda Function URLs provide a simpler way to expose a Lambda function over HTTP.

| Feature         | API Gateway      | Lambda Function URL   |
| --------------- | ---------------- | --------------------- |
| HTTP endpoints  | Yes              | Yes                   |

| Usage plans     | REST API support | No                    |

### 11\. Event Filtering and Event Source Mapping Configuration

Filtering allows Lambda to process only relevant events.

Without filtering, every event delivered by a source might trigger unnecessary computation.

### 11.1 Event filtering

Consider a DynamoDB table containing:

```json
{
  "status": "PENDING"
}
```

You might want Lambda to process only records where the status is `COMPLETED`.

Event source mappings support filtering criteria for supported event sources, including SQS, Kinesis, and DynamoDB Streams.

Example filter pattern:

```json
{
  "dynamodb": {
    "NewImage": {
      "status": {
        "S": ["COMPLETED"]
      }
    }
  }
}
```

This filters DynamoDB stream records based on the new image.

For SQS, filtering can inspect supported message body and message attribute structures.

For EventBridge and SNS, filtering is configured through their respective rules and subscription policies rather than Lambda event source mappings.

### 11.2 Event source mapping configuration

Important configuration options include:

| Configuration           | Purpose                                                    |
| ----------------------- | ---------------------------------------------------------- |
| Batch size              | Maximum records per invocation                             |
| Maximum batching window | Maximum time to collect records                            |
| Starting position       | Where stream processing begins                             |
| Enabled                 | Enables or disables mapping                                |
| Filter criteria         | Selects relevant records                                   |
| Maximum concurrency     | Limits concurrent processing for supported mappings        |
| Parallelization factor  | Increases parallel processing of stream shards             |
| Retry attempts          | Controls retry behavior where supported                    |
| Maximum record age      | Limits how long records can remain eligible for processing |
| On-failure destination  | Stores information about failed stream batches             |

Not every setting is supported by every event source.

For example, SQS uses queue visibility and redrive configuration, while DynamoDB Streams and Kinesis have stream-specific retry and failure-handling settings.

### 11.3 Batch size and batching window

Batch size determines how many records Lambda can receive in a single invocation.

The batching window determines how long Lambda can wait to collect records before invoking the function.

These settings help balance:

* Processing latency.

* Invocation overhead.

* Throughput.

* Cost.

* Memory utilization.

A larger batch can improve throughput but may increase processing duration and the impact of failures.

### 12\. Batch Processing and Partial Batch Failure Handling

Batch processing is especially important when integrating Lambda with SQS, DynamoDB Streams, and Kinesis.

Instead of invoking Lambda once per record, AWS groups multiple records into a single invocation.

### 12.1 Why batch processing matters

Imagine processing 10,000 messages.

Processing each message individually creates many Lambda invocations.

Batching can reduce invocation overhead and improve throughput.

However, batch processing introduces a challenge: how do you handle a batch containing both successful and failed records?

### 12.2 Partial batch responses

For supported event sources, Lambda allows a function to report individual failed records.

The response uses:

```json
{
  "batchItemFailures": [
    {
      "itemIdentifier": "record-sequence-number"
    }
  ]
}
```

The identifier depends on the event source:

* SQS: message ID.

* DynamoDB Streams: sequence number.

* Kinesis: sequence number.

The response must be enabled in the event source mapping.

### 12.3 Bisect batch on error

For DynamoDB Streams and Kinesis, Lambda also supports bisecting a failed batch.

For example:

```text
Original batch: 100 records
         |
         v
      Failure
         |
         v
    Split into 2
      /     \
     v       v
  50 records 50 records
     |         |
     v         v
  Process    Process
```

This helps isolate problematic records without repeatedly retrying the entire original batch.

However, it does not replace proper application-level error handling.

### 12.4 Choosing a processing strategy

| Strategy                   | Best suited for                            |
| -------------------------- | ------------------------------------------ |
| Process entire batch       | Simple, independent records                |
| Partial batch response     | Independent records with isolated failures |
| Bisect batch               | Stream batches with problematic records    |
| DLQ or failure destination | Persistent processing failures             |
| Idempotent processing      | Duplicate delivery protection              |

### 14\. Event Ordering, Duplicate Events, and Idempotency

This is one of the most important topics when developing production-grade event-driven applications.

A common misconception is that Lambda processes every event exactly once and in the order it was generated.

That is not generally true.

### 14.1 At-least-once delivery

Many AWS event integrations use at-least-once delivery semantics.

This means an event might be delivered more than once.

For example:

```text
Order Created
      |
      v
SQS Queue
      |
      v
Lambda
      |
      v
Database Updated
      |
      v
Unexpected Failure
      |
      v
Message Retried
      |
      v
Lambda Executes Again
```

The database update might already have succeeded before the function failed.

When Lambda receives the same message again, it could perform the operation twice.

This can cause serious problems.

For example:

* Duplicate payments.

* Duplicate orders.

* Repeated email notifications.

* Incorrect inventory calculations.

* Duplicate database records.

### 14.2 What is idempotency?

An operation is idempotent when executing it multiple times produces the same intended final result as executing it once.

For example, consider an order with ID `ORD-1001`.

Instead of blindly creating an order every time an event arrives, the application checks whether the order has already been processed.

Simplified Python example:

```python
def process_order(order_id):
    if order_already_processed(order_id):
        return

    create_order_record(order_id)

    mark_order_as_processed(order_id)
```

This is a basic illustration. In production, checking and marking must be designed atomically to prevent concurrent executions from both processing the same order.

You can implement idempotency using:

* DynamoDB conditional writes.

* Unique database constraints.

* Idempotency keys.

* Transactional operations.

* Dedicated idempotency records.

### 14.3 Event ordering

Different AWS integrations provide different ordering guarantees.

| Integration      | Ordering behavior             |
| ---------------- | ----------------------------- |
| SQS Standard     | Best effort                   |
| SQS FIFO         | Within message groups         |
| DynamoDB Streams | Per shard                     |
| Kinesis          | Per shard and partition key   |
| SNS Standard     | No general ordering guarantee |
| EventBridge      | No general ordering guarantee |
| S3 notifications | No guaranteed ordering        |

When ordering matters, choose the architecture accordingly.

For example, an order-processing system might use:

```text
Message Group ID = customer_id
```

With an SQS FIFO queue, events belonging to the same customer can be processed in order within that message group.

### 14.4 Designing reliable event consumers

A reliable Lambda consumer should consider:

* Duplicate event delivery.

* Out-of-order events.

* Partial processing failures.

* Retry behavior.

* Poison messages.

* Concurrent executions.

* Idempotency.

* Event retention and recovery.

Key principle: Never build a critical business workflow on the assumption that an event will be processed exactly once.

Design consumers to tolerate repeated delivery.

### 15\. EventBridge Scheduler and Scheduled Lambda Execution

Not every Lambda invocation needs to be triggered by an application event.

Sometimes you need a function to execute at a particular time or on a recurring schedule.

Examples:

* Generate daily reports.

* Clean up expired records.

* Send scheduled notifications.

* Synchronize external systems.

* Run periodic maintenance tasks.

* Process recurring billing operations.

AWS provides EventBridge Scheduler for this purpose.

![Amazon EventBridge Scheduler to AWS Lambda | Serverless Land](https://images.openai.com/static-rsc-4/q33WCjdt6grD5M7McbMbylDIuoCXPeRjEk4bqHafMliwqxDNaQZY5csv4ghyLK-p85ii57KEgZxlNJvJmjmqG6El-9uWKRN4_GxlsJhZNMkVWcS3mmpEWjJC4v-I_vc2MDDyGUuteyoDj4PxJsp-M0Oak40vXhp5bmgIFMHK5_FpqXdBnm8SogdCTuLSwkaC?purpose=fullsize)

### 15.1 EventBridge Scheduler

EventBridge Scheduler is a serverless scheduling service that can invoke Lambda functions and other supported targets.

It supports:

* One-time schedules.

* Recurring schedules.

* Rate-based schedules.

* Cron-based schedules.

* Time zones.

* Flexible time windows.

* Retry policies.

* Dead-letter queues.

### 15.2 Rate-based schedules

A rate expression executes a target at regular intervals.

For example:

```text
rate(5 minutes)
```

This schedules execution every five minutes.

Other examples:

```text
rate(1 hour)
rate(1 day)
rate(7 days)
```

### 15.3 Cron-based schedules

Cron expressions allow more precise scheduling.

For example:

```text
cron(0 9 * * ? *)
```

This represents a daily schedule at 09:00 UTC.

Another example:

```text
cron(0 2 ? * MON-FRI *)
```

This represents 02:00 UTC every weekday.

AWS cron expressions have six fields:

```text
Minutes Hours Day-of-month Month Day-of-week Year
```

Note that EventBridge Scheduler supports time zones, so you can schedule tasks using a local time zone rather than manually converting everything to UTC.

### 15.4 One-time schedules

You can schedule a Lambda invocation for a specific date and time.

For example:

```text
2026-12-25T09:00:00
```

This is useful for:

* Scheduled notifications.

* Appointment reminders.

* Temporary resource cleanup.

* Time-specific business operations.

One-time schedules can be configured for automatic deletion after completion.

### 15.5 Scheduler versus EventBridge scheduled rules

There are two related scheduling mechanisms:

| Feature               | EventBridge Scheduler    | Scheduled EventBridge Rules |
| --------------------- | ------------------------ | --------------------------- |
| One-time schedules    | Yes                      | No                          |
| Recurring schedules   | Yes                      | Yes                         |
| Time zones            | Yes                      | UTC-based scheduling        |
| Flexible time windows | Yes                      | No equivalent               |
| AWS recommendation    | Preferred for scheduling | Legacy scheduling approach  |

For new scheduling requirements, prefer EventBridge Scheduler.

### 15.6 Security and execution permissions

EventBridge Scheduler uses an execution role to invoke its target.

For Lambda, this role needs the appropriate permission to invoke the function.

The execution role is separate from the Lambda function's execution role.

This distinction is important:

* Scheduler execution role: Allows Scheduler to invoke Lambda.

* Lambda execution role: Allows Lambda to access AWS resources during execution.

### 16\. Important Architecture and Operational Considerations

Before moving to the next module, it is worth bringing together several concepts that affect almost every Lambda integration.

### 16.1 Push versus polling

| Characteristic       | Push integrations            | Polling integrations                   |
| -------------------- | ---------------------------- | -------------------------------------- |
| Invocation           | Source invokes Lambda        | Lambda reads source                    |
| Examples             | S3, SNS, EventBridge         | SQS, Kinesis, DynamoDB Streams         |
| Event source mapping | Usually not required         | Required                               |
| Batching             | Depends on integration       | Configurable                           |
| Scaling              | Depends on source and Lambda | Depends on polling and source capacity |
| Failure handling     | Source-specific              | Source-specific                        |

### 16.2 Understand the permission model

For each integration, identify both sides of the permission relationship.

For example:

S3 → Lambda

* S3 needs permission to invoke Lambda.

* Lambda needs permission to read the S3 object.

SQS → Lambda

* Lambda's execution role needs permissions to poll and consume messages.

* Lambda needs permission to perform its business operations.

EventBridge → Lambda

* Lambda needs a resource-based permission allowing the relevant EventBridge rule to invoke it.

* Lambda's execution role needs permissions for its business operations.

Scheduler → Lambda

* Scheduler needs an execution role allowing it to invoke Lambda.

* Lambda's execution role controls what the function can do afterward.

### 16.3 Monitoring event-driven integrations

You should monitor more than just Lambda errors.

Important metrics include:

| Service          | Useful metrics                                                    |
| ---------------- | ----------------------------------------------------------------- |
| Lambda           | Invocations, Errors, Duration, Throttles                          |
| SQS              | ApproximateNumberOfMessagesVisible, ApproximateAgeOfOldestMessage |
| SNS              | NumberOfMessagesPublished, NumberOfNotificationsFailed            |
| Kinesis          | IteratorAgeMilliseconds, ReadProvisionedThroughputExceeded        |
| DynamoDB Streams | IteratorAge                                                       |
| EventBridge      | Invocations, FailedInvocations, ThrottledRules                    |
| API Gateway      | Count, 4XXError, 5XXError, Latency                                |
| ALB              | RequestCount, HTTPCode_ELB_5XX_Count, TargetResponseTime          |

A growing SQS queue or increasing Kinesis iterator age can indicate that your Lambda consumers are not keeping up with incoming traffic.

* SQS vs SNS: SQS queues messages for consumers; SNS distributes messages to subscribers.

* SNS vs EventBridge: SNS focuses on pub/sub; EventBridge provides sophisticated event routing.

* DynamoDB Streams vs Kinesis: DynamoDB Streams capture database changes; Kinesis handles general-purpose streaming data.

* Push vs polling: Direct integrations invoke Lambda; event source mappings allow Lambda to poll supported sources.

* Execution role vs resource policy: One controls what Lambda can access; the other controls who can invoke Lambda.

* At-least-once delivery vs idempotency: Duplicate delivery is possible, so consumers must safely handle repeated events.
